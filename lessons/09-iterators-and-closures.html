Iterators & Closures

Iterators and closures are where Rust starts to feel functional. Chains of map, filter, and collect replace manual loops — and because iterators are lazy, nothing runs until you ask for a result.

⏱ 18 min 🦀 Beginner ✎ 1 exercise ✓ Completed
1

Read

The idea

A closure is an anonymous function that can capture variables from its environment. An iterator is a sequence you can transform and consume. Together they let you express “take these items, keep the ones that match, transform them, and sum the result” as a short, readable pipeline.

Closures

main.rs
fn main() {
    let double = |n: i32| n * 2;
    println!("{}", double(21));

    let base = 10;
    let add_base = |n| n + base; // captures base by reference
    println!("{}", add_base(5));
}

The parameter and return types can usually be inferred from the first use. A closure that only borrows its environment implements Fn; one that mutates captured variables implements FnMut; one that consumes them implements FnOnce. Most of the time you do not write these bounds by hand.

main.rs
fn main() {
    let name = String::from("Ferris");

    // move forces the closure to take ownership of name
    let greet = move || println!("Hello, {name}!");

    greet();
    // println!("{name}"); // error: name was moved into the closure
}

Without move, the closure would borrow name. The move keyword is essential when a closure outlives the current scope, such as when you spawn a thread.

Iterators are lazy

Calling .map(...) or .filter(...) does not process anything. It builds an adapter that describes the work. The work happens when a consuming method such as collect, sum, or for_each asks for items:

main.rs
fn main() {
    let numbers = vec![1, 2, 3, 4, 5, 6];

    let evens: Vec<i32> = numbers
        .iter()
        .copied()
        .filter(|n| n % 2 == 0)
        .collect();

    println!("{evens:?}"); // [2, 4, 6]
}

iter() yields references, iter_mut() yields mutable references, and into_iter() consumes the collection and yields owned values. That is why .copied() appears above: it turns &i32 into i32 so the result can own its elements.

map(f)Transform every item with f.
filter(p)Keep items for which p returns true. The closure receives a reference to the item.

zip(other)Pair items from two iterators.
chain(other)Concatenate two iterators.
ConsumerWhat it returns

main.rs
fn main() {
    let total: i32 = (1..=10)
        .filter(|n| n % 2 == 0)
        .map(|n| n * n)
        .sum();

    println!("{total}"); // 220

    for (index, name) in ["Ada", "Linus", "Ferris"].iter().enumerate() {
        println!("{index}: {name}");
    }

    let sum = (1..=5).fold(0, |acc, n| acc + n);
    println!("{sum}"); // 15
}

Iterator chains compile down to code as efficient as a hand-written loop, sometimes better because the compiler can eliminate bounds checks. Prefer them when they make the intent clearer; a plain for loop is still perfectly idiomatic when the body has side effects or complex control flow.

The compiler is your type checker for chains

When a chain does not compile, add an explicit type annotation at the collect and split the chain into temporary variables. Most iterator errors are about whether the closure receives T or &T.

Four questions. Get three or more right to complete the lesson — you can retry as often as you like.





01When does an iterator chain actually do its work?



Why: Adapters are lazy: they only describe a transformation. A consumer drives the iteration and produces a value. This lets the compiler fuse the steps into one efficient loop.



02What does the closure in .filter(|n| n % 2 == 0) receive?



Why: filter passes &Self::Item to its predicate, so an iterator of i32 gives the closure &i32. Use *n when you need the owned value.



03Why does let evens: Vec<i32> = numbers.iter().filter(...).collect(); include a type annotation?



Why: collect is generic over the result type. Without an annotation, the compiler may not know whether you want a Vec, a HashSet, a String, or something else.



04What does a move closure do?



Why: move makes the closure capture by value instead of by reference. This is necessary when the closure must outlive the current scope, for example when moving it into a thread.
