Modules, Crates & Testing

A single main.rs stops scaling quickly. Split code into modules, pull in libraries from crates.io, and use Cargo's test runner to prove the pieces work — then go build something.

⏱ 22 min 🦀 Beginner ✎ 1 exercise ✓ Completed
1

Read

The idea

So far every example has lived in one file. Real projects have many. Rust organises code with modules inside a crate, and crates inside a package. The rules are small: items are private by default, and pub opens them up.

Modules and privacy

main.rs
mod greetings {
    pub fn hello(name: &str) -> String {
        format!("Hello, {name}!")
    }

    fn secret() -> &'static str {
        "internal"
    }
}

use greetings::hello;

fn main() {
    println!("{}", hello("Ferris"));

    // greetings::secret(); // error: function is private
}

A module is a namespace. By default its contents are visible only inside the module and its descendants. pub exposes an item to the parent, and the parent can re-export it with pub use. use brings a path into scope without changing where the item lives.

For larger projects, put modules in their own files. mod greetings; in main.rs loads src/greetings.rs (or src/greetings/mod.rs):

project layout
src/
├── main.rs          # mod greetings; use greetings::hello;
├── greetings.rs     # pub fn hello(...)
├── models.rs        # pub mod user; pub mod post;
└── models/
    ├── user.rs
    └── post.rs

Paths work like file paths: crate::greetings::hello starts at the crate root, super:: refers to the parent module, and self:: to the current one. Keep modules focused, and keep the public surface small.

Packages, crates, and dependencies

A package is a directory with a Cargo.toml. It contains one or more crates: a binary crate rooted at src/main.rs, a library crate rooted at src/lib.rs, or both. A library can be used by the binary and by other projects.

External crates come from crates.io. Add one with Cargo, which updates Cargo.toml and Cargo.lock:

terminal
cargo add serde --features derive
Cargo.toml
[package]
name = "my_app"
version = "0.1.0"
edition = "2021"

[dependencies]
serde = { version = "1", features = ["derive"] }

Then use serde::{Serialize, Deserialize}; and derive the traits. Dependencies are compiled once and cached; Cargo.lock pins exact versions so everyone on the team builds the same code. Audit dependencies you add: each one is code you now trust.

Tests live next to the code

Rust has a built-in test runner. Mark test functions with #[test], put them in a module gated by #[cfg(test)], and run cargo test:

main.rs
pub fn add(a: i32, b: i32) -> i32 {
    a + b
}

#[cfg(test)]
mod tests {
    use super::*; // bring add() into scope

    #[test]
    fn adds_positive_numbers() {
        assert_eq!(add(2, 3), 5);
    }

    #[test]
    fn adds_negative_numbers() {
        assert_eq!(add(-2, -3), -5);
    }
}
  • #[test] marks a function as a test. It takes no arguments and returns nothing.
  • assert!, assert_eq!, and assert_ne! panic with a useful message when the condition fails.
  • #[cfg(test)] means the module is compiled only for tests, so test code never ships in release builds.
  • use super::* imports the parent module's items, giving tests access to private functions in the same module.
  • #[should_panic(expected = "...")] asserts that a test panics with a message containing the given text.

Run the suite with cargo test. Cargo compiles the crate in test mode and runs every #[test] in parallel. You will see a summary like:

cargo test
running 2 tests
test tests::adds_negative_numbers ... ok
test tests::adds_positive_numbers ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

Integration tests go in the tests/ directory at the package root. Each file there is compiled as a separate crate, so it can only use your public API:

main.rs
// tests/integration.rs
use my_crate::add;

#[test]
fn adds_from_outside() {
    assert_eq!(add(1, 2), 3);
}

Documentation comments (///) can contain code blocks. cargo test compiles and runs those too, which keeps examples in your docs honest. That is three layers of tests — unit, integration, and documentation — with no extra framework.

The day-to-day toolkit

CommandWhat it is for
cargo checkFast type-check while editing.
cargo fmtFormat code with rustfmt — stop arguing about style.
cargo clippyRun hundreds of extra lints for idiomatic code.
cargo testRun unit, integration, and doc tests.
cargo doc --openBuild documentation from doc comments and open it.
cargo build --releaseOptimised build for distribution.

Where to go next

  • Read The Rust Programming Language — it goes deeper on every topic here.
  • Work through Rustlings for short compiler-error exercises.
  • Build a CLI with clap, a web service with axum, or an async tool with tokio.
  • When you hit a borrow-checker error, reduce it to a tiny example and read the compiler's suggestion. It is usually right.
The finish line is a starting line

You now know enough Rust to read real code and be dangerous in a good way. Pick a small project you would otherwise write in another language, port it, and let the compiler teach you the rest.

01What does pub do to an item?



Why: Items are private by default. pub exposes them to the parent module, and enough pub along the path makes them reachable from outside the crate.



02Which attribute marks a function as a test?



Why: #[test] registers the function with the test harness. #[cfg(test)] controls whether a whole module is compiled in test builds.



03Which command runs your test suite?



Why: cargo test compiles the crate in test mode and runs unit, integration, and documentation tests. cargo check only type-checks.



04Why wrap test modules in #[cfg(test)]?



Why: #[cfg(test)] is a conditional-compilation attribute. It keeps test-only helpers and tests out of production binaries, reducing size and avoiding unused-code warnings.
