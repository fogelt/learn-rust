Option, Result & Errors

Rust has no exceptions and no null. Missing values use Option, recoverable failures use Result, and the question mark operator propagates errors without hiding them.

⏱ 20 min 🦀 Beginner ✎ 1 exercise ✓ Completed
1

Read

The idea

Many languages handle failure in two ways: throw an exception and hope someone catches it, or return null and hope someone checks. Rust makes both cases part of the type system, so the compiler can see whether you handled them.

Panics: unrecoverable bugs

A panic aborts the current operation. You cannot catch it in normal code (well, catch_unwind exists, but it is for special cases). Use panics for broken invariants, not for expected failures like bad user input:

main.rs
fn main() {
    let values = vec![1, 2, 3];

    // index 99 does not exist: this panics at runtime
    println!("{}", values[99]);
}

A panic prints a message and unwinds the stack, running destructors as it goes. In a library, treat panics as a last resort — callers cannot easily recover from them.

Option: a value might be absent

main.rs
fn find_score(name: &str) -> Option<u32> {
    if name == "ferris" {
        Some(42)
    } else {
        None
    }
}

fn main() {
    match find_score("ferris") {
        Some(score) => println!("score: {score}"),
        None => println!("no score"),
    }

    let fallback = find_score("nobody").unwrap_or(0);
    println!("fallback: {fallback}");
}

unwrap extracts the value or panics on None. Use it when absence would be a bug, or in tiny examples. In real code prefer match, if let, unwrap_or, or ?.

Result: an operation might fail

Result<T, E> has two variants: Ok(T) for success and Err(E) for failure. The error carries information about what went wrong.

main.rs
fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err(String::from("cannot divide by zero"))
    } else {
        Ok(a / b)
    }
}

fn main() {
    match divide(10.0, 2.0) {
        Ok(value) => println!("{value}"),
        Err(message) => println!("error: {message}"),
    }
}

Parsing is the canonical example. str::parse returns a Result because text is not always a number:

main.rs
fn main() {
    let good: i32 = "42".parse().expect("not a number");
    println!("{good}");

    match "oops".parse::<i32>() {
        Ok(number) => println!("parsed {number}"),
        Err(error) => println!("could not parse: {error}"),
    }
}

expect is like unwrap but takes a message that appears in the panic. It still panics, so it is for cases where failure is genuinely impossible or indicates a bug.

Propagating with ?

Most functions should not decide how to handle an error. The ? operator says: if the result is Err, return it from the current function; otherwise unwrap the Ok and continue.

main.rs
use std::fs;

fn read_username() -> Result<String, std::io::Error> {
    let text = fs::read_to_string("username.txt")?;
    Ok(text.trim().to_string())
}

fn main() {
    match read_username() {
        Ok(name) => println!("hello, {name}"),
        Err(error) => println!("could not read file: {error}"),
    }
}

You can use ? only in a function that returns a compatible Result (or Option). The error type must be convertible into the function's error type. main can return a Result too:

main.rs
use std::error::Error;

fn main() -> Result<(), Box<dyn Error>> {
    let number: i32 = "42".parse()?;
    println!("{number}");
    Ok(())
}

Here Box<dyn Error> is a boxed trait object that can hold many error types. It is convenient for small binaries; libraries usually define a concrete error enum. The anyhow and thiserror crates are popular helpers once your error types grow.

ToolUse it when…
match / if letYou need to handle each case explicitly.
unwrap_or(default)A sensible fallback exists.
unwrap() / expect(msg)Failure is a bug and panicking is acceptable.
?You want to propagate the error to the caller.
unwrap_or_else(f)You need to compute the fallback lazily or log the error.
Option is not Result

Option says a value may be absent; that is not necessarily an error. Result says an operation failed and carries a reason. Choosing the right one makes APIs self-documenting.

01Which type should a function return when an operation can fail in a recoverable way?



Why: Result<T, E> carries either a success value or an error value with details. Option only expresses presence or absence, and a panic cannot be handled by the caller.



02What does the ? operator do?



Why: ? propagates the error to the caller using the From conversion, so the function's error type must be compatible. It replaces a lot of boilerplate match expressions.



03What happens if you call unwrap() on an Err?



Why: unwrap panics on Err (and None). That is acceptable in tests and examples, but user input and I/O should be handled or propagated.



04What is the difference between Option and Result?



Why: A missing middle name is Option; a failed file read is Result. The distinction keeps “nothing here” separate from “this went wrong, and here is why”.
