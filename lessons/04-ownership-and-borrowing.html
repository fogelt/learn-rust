Ownership & Borrowing

Ownership is the idea that makes Rust different. One value has one owner; borrowing lets other code look without taking it. Learn the rules once and the borrow checker becomes an ally.

⏱ 24 min 🦀 Beginner ✎ 1 exercise ✓ Completed
1

Read

The idea

Most languages manage memory with a garbage collector or by making you call free. Rust uses a third approach: the compiler tracks which part of your code owns each value, and inserts the cleanup automatically at the right moment. The rules are simple — enforcing them is the clever part.

The three ownership rules

  1. Every value has exactly one owner.
  2. There can only be one owner at a time.
  3. When the owner goes out of scope, the value is dropped (its memory is freed).
main.rs
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // ownership moves from s1 to s2

    println!("{s2}");

    // println!("{s1}"); // error[E0382]: borrow of moved value: s1
}

A String is a small struct on the stack — pointer, length, capacity — pointing at bytes on the heap. Assignment does not copy the heap bytes; it moves the pointer. Rust then invalidates s1. If both names stayed usable, both would free the same allocation at the end of scope: a double free. The compiler forbids it.

Types that live entirely on the stack and are cheap to copy implement the Copy trait. For them, assignment copies instead of moving:

main.rs
fn main() {
    let x = 5;
    let y = x;

    println!("{x} and {y}"); // both are valid
}

Integers, floats, bool, char, and tuples or arrays made entirely of Copy types are Copy. String, Vec, and HashMap are not.

If you genuinely need two independent heap values, clone explicitly:

main.rs
let s1 = String::from("hello");
let s2 = s1.clone();
println!("{s1} {s2}"); // both valid

clone can be expensive. Reaching for it to silence the borrow checker is usually a design smell; borrowing is normally what you want.

Moving into functions

main.rs
fn consume(message: String) {
    println!("{message}");
}

fn main() {
    let msg = String::from("hello");
    consume(msg); // msg is moved into the function

    // println!("{msg}"); // error: value borrowed here after move
}

Passing a String by value transfers ownership. The function drops it when it returns. To let the caller keep the value, pass a reference instead.

Borrowing with references

main.rs
fn length(text: &str) -> usize {
    text.len()
}

fn main() {
    let message = String::from("hello");
    let len = length(&message); // borrow, do not move

    println!("{message} has {len} bytes");
}

The & creates a reference. The function reads through it but does not own the String, so message is still usable afterwards. Here &String is automatically coerced to &str — a more flexible borrowed string type.

Immutable references can be shared freely:

main.rs
let message = String::from("hello");
let a = &message;
let b = &message;

println!("{a} {b}"); // fine: many readers

If a function needs to change the value, borrow it mutably. The binding itself must be mut too:

main.rs
fn add_suffix(text: &mut String) {
    text.push_str("!");
}

fn main() {
    let mut message = String::from("hello");
    add_suffix(&mut message);
    println!("{message}"); // hello!
}

The borrowing rules

One rule to remember

At any given time, you can have either any number of immutable references (&T) or exactly one mutable reference (&mut T) — never both. Every reference must always be valid.

Why so strict? A mutable reference is exclusive access, and immutable references are shared access. Allowing both at once would let one part of your code change a value while another is reading it — the classic data race. Rust moves that bug from runtime to compile time.

Borrows end at their last use, not at the end of the block. Thanks to this non-lexical lifetime analysis, sequential borrows are fine:

main.rs
let mut text = String::from("hi");

let first = &text;
println!("{first}"); // last use of first

text.push_str("!");  // okay: the immutable borrow has ended

Rust also prevents dangling references. You cannot return a reference to a local value that is about to be dropped; the compiler will reject it. Lesson 8 shows how lifetime annotations describe these relationships when the compiler needs help.

Slices: borrowing part of a collection

main.rs
fn main() {
    let text = String::from("hello world");
    let hello = &text[0..5];
    let world = &text[6..11];

    println!("{hello} / {world}");

    let numbers = [1, 2, 3, 4, 5];
    let middle = &numbers[1..4];
    println!("{middle:?}"); // [2, 3, 4]
}

A string slice (&str) points into an existing string and carries a length. An array slice (&[T]) works the same way. Slicing by byte index can panic if the index is not on a character boundary — more on that in lesson 6.

How to stop fighting the borrow checker

When a value is moved and you still need it, first ask: does this function really need to own it? Change the parameter to &T or &mut T. Reach for clone() only when you truly need an independent copy.

01After let b = a; where a is a String, what happens to a?



Why: Assignment moves ownership for non-Copy types. Using a afterwards is a compile error. To keep both usable, borrow with &a or clone explicitly.



02Which combination of references is allowed at the same time?



Why: Many readers or exactly one writer, never both. Immutable references (&T) can be shared freely because nobody can change the value through them.



03How can a function read a String without taking ownership?



Why: Borrowing with &str (or &String) lets the caller keep ownership. Passing by value moves the string into the function, and it is dropped when the function returns.



04What does the borrow checker guarantee?



Why: Ownership and borrowing are checked at compile time. They rule out use-after-free and data races, but they do not prevent panics from explicit panic! calls or out-of-bounds indexing.
